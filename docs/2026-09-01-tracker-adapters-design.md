# Tracker adapters — design

Статус: **предложено**, ожидает утверждения.
Дата: 2026-09-01.

## Проблема

Плагин приварен к ClickUp: 24 упоминания в `skills/worklog-day/SKILL.md`,
9 в `scripts/resolve-config.sh`, `allowed-tools` в `commands/log-day.md`
перечисляет `mcp__clickup__*`. Появился второй реальный трекер — Asana, — и
приваренность стала блокирующей.

При этом **ценная половина плагина от трекера не зависит уже сейчас**:
`collect-window.sh` (сбор окна из GitHub с привязкой к аутентифицированному
пользователю), `validate-draft.sh`, `lib.sh`, контракт черновика, правила
менеджерского голоса и антиспама, согласование времени глагола со статусом,
дедуп по номерам PR и гейт перед записью. Дублировать это ради второго трекера
означало бы получить две копии, которые немедленно начнут расходиться.

### Протечка в контракте

Контракт черновика объявляет `parent: "umbrella"` — значение, которое
резолвится в `umbrella_task_id` из конфига. То есть **черновик знает про
устройство доски**, хотя должен описывать только форму работы.

Хуже: необязательность umbrella объявлена (`SKILL.md`: «+ optional
`umbrella_task_id`»), но не обработана. Рецепт S3 для самостоятельной записи
предписывает привязать её к `eff.umbrella_task_id` — если он не задан,
привязывать не к чему, и поведение не определено.

## Решение

Три слоя с явной границей.

```
ядро (SKILL.md)          scope → gather → draft → ГЕЙТ → write → links
                         о конкретном трекере не знает ничего
        │
контракт (format.md)     единственный интерфейс между ядром и адаптером
        │                описывает форму работы, а не устройство доски
        ▼
адаптер                  references/adapters/<tracker>.md
                         объявленные возможности + маппинг + рецепт вызовов
```

### Почему «адаптер», а не «бэкенд»

Бэкенд подразумевает ярус, за которым что-то лежит. ClickUp и Asana ни за чем
не лежат — это внешние системы, чей интерфейс мы переводим в свой. Это
буквально паттерн Adapter: клиент — контракт черновика, адаптируемое — API
трекера.

## Изменения контракта

**`parent: "umbrella"` и `parent: "none"` схлопываются в `parent: "root"`.**

Черновик перестаёт знать, существует ли мастер-задача. Он заявляет только
структуру:

```
parent: "root"              запись верхнего уровня
parent: "<код контейнера>"  дочерняя к контейнеру из containers
parent: "<id задачи>"       дочерняя к существующей задаче
```

Куда это ляжет — решают адаптер и конфиг:

```
мастер-задача задана    → верхнеуровневые дополнительно к ней привязываются
мастер-задача не задана → верхнеуровневые остаются просто верхнеуровневыми
```

Это ломающее изменение контракта, но цена нулевая: черновики — ежедневные
эфемерные файлы, мигрировать нечего.

## Объявление возможностей

Трекеры не эквивалентны, и прятать это за общим знаменателем — значит опустить
ClickUp до уровня Asana. Поэтому каждый адаптер объявляет, что умеет, а ядро
подстраивается:

| Ключ | Значения | Зачем ядру |
| --- | --- | --- |
| `rich_text` | `markdown` / `html_subset` / `plain` | как рендерить человеческий блок |
| `nesting` | `native` / `link` | как выражать вложенность |
| `status` | `named` / `section` / `completed_flag` | как выражать «сделано» |
| `assignees` | `many` / `single` | сузить ли список |
| `cross_links` | `native` / `permalink` | чем связывать задачи |

## Конфигурация

```json
{
  "tracker": "asana",
  "asana": { "project_gid": "…", "section_map": { "done": "…", "in progress": "…" } }
}
```

**Обратная совместимость бесплатная:** если `tracker` не задан, но есть
`clickup_list_id` — считаем `clickup`. Существующие конфиги продолжают работать
без правок.

`resolve-config.sh` перестаёт знать про ClickUp: обязательная привязка
определяется таблицей «трекер → требуемые ключи».

## Специфика Asana — измеренная, а не предположенная

Проверено на доске `1217990719469934` (workspace `1209252743810964`):

- **Статус несут секции**, а не флаг: Backlog / To Do / In Progress /
  Ready for Review / Done (`1217988309530635`). Задача в Done имеет
  `completed: false` — перетаскивание карточки флаг не меняет.
- **Решено:** закрывая задачу, переносим в Done **и** ставим `completed: true`.
  Ожидание приёмки вынесено в отдельную секцию Ready for Review, значит Done
  терминален; иначе отчёты Asana вечно считали бы проект незавершённым.
- **Поля Story Points нет** и не нужно: SP пишутся текстом в описание —
  ровно как в ClickUp, где кастомное поле тоже никогда не использовалось.
- **Markdown не поддерживается.** Есть `html_notes` с подмножеством:
  `<h1> <h2> <strong> <em> <code> <pre> <ul> <ol> <li> <a> <blockquote> <hr/> <img>`.
  Человеческий блок использует заголовки, жирный, ссылки и эмодзи — ложится
  один в один.
- **Подзадача может одновременно быть участником проекта и секции:** в
  `create_tasks` поля `parent`, `project_id` и `section_id` независимы.
  Схема это разрешает; поведение сервера подтвердить на первом прогоне.
- **Мастер-задачи нет и не нужно** — группировку делают секции.

## Тесты

`scripts/tests/test-skill.sh` проверяет наличие в `SKILL.md` строк
`clickup_create_task` и `clickup_add_task_link`. После выноса ClickUp в адаптер
эти проверки станут ложными — их надо переписать, а не удалить: они должны
проверять, что **ядро не упоминает ни одного трекера**, а каждый адаптер
объявляет полный набор ключей возможностей.

Добавляется `test-adapters.sh`.

## Границы

Рантайма нет: адаптер — документ-рецепт, которому следует модель, а не код с
интерфейсом. Значит гарантия слабее, чем у типизированного контракта — неверный
рецепт даст неверное поведение молча. Страхуют `validate-draft.sh`, гейт перед
записью и тесты структуры.

Цена третьего трекера: один файл адаптера, строка в таблице требуемых ключей
`resolve-config.sh` и дополнение `allowed-tools`. Последнее — статичный список
во frontmatter, автоматически он не расширяется.

## Состояние репозитория на момент написания

Разбор расхождения истории (2026-09-01):

- Локальная `main` и `origin/main` **разошлись**: origin впереди на 14
  коммитов, локальная — на 5, различия в 10 файлах. Судя по одинаковым
  сообщениям при разных SHA, историю на origin переписали.
- Содержательно origin — это та же работа плюс **нормализация**: `~/.claude/…`
  заменено на `$HOME/.claude/…`, из `SKILL.md` убраны русские триггеры
  («вчера», «с #N»). Уникальная работа локальной линии (multi-umbrella,
  native subtask nesting) на origin присутствует.
- **Установленная и реально работающая копия** (`~/.claude/plugins/cache/
  worklog-dev/worklog/0.1.0`) соответствует ЛОКАЛЬНОЙ линии: русские триггеры
  в ней есть. То есть на линии origin `/log-day вчера` перестанет срабатывать.
- Решение: ничего не разрушать. Работа идёт в ветке `feat/tracker-adapters`,
  созданной от `origin/main`; локальная `main` оставлена нетронутой на
  `0d925f7` как запись прежней линии.
- Тесты `scripts/tests/run-all.sh` зелёные на обеих линиях.

## Незакрытые пункты

1. **Вернуть русские триггеры** отдельным коммитом — не откатом нормализации,
   а расширением: триггеры принимают и русские, и английские формулировки.
   Пользователь ими пользуется; на линии origin это регресс.
2. **Подрезать таблицу возможностей.** Несущие ключи — `rich_text` и `status`.
   `assignees` и `cross_links` выведены умозрительно, на двух трекерах могут
   оказаться церемонией. Оставлять только то, что реально меняет поведение ядра.
3. **Защита от выбора не того адаптера.** Ядро обязано явно резолвить адаптер
   по ключу `tracker` и вслух объявлять, какой использует. Нужен тест: ядро не
   упоминает ни один трекер, адаптер ровно один на файл.
4. **Подтвердить поведение Asana на первом прогоне:** подзадача с
   одновременными `parent` + `project_id` + `section_id`; перенос между
   секциями у существующей задачи (`add_projects` с `section_id` может
   оказаться no-op для уже состоящей в проекте — фоллбэк
   `remove_projects` + `add_projects`).
5. **Установка в проект-потребитель.** После доводки плагин ставится локально
   в kidi-builder; его `.gitignore` не разрешает `.claude/plugins/`, поэтому
   установленная копия останется вне git автоматически.
