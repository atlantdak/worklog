# Plan → Board: планируемая работа на доске трекера

- **Статус:** дизайн, редакция 2 после внешнего ревью
- **Дата:** 2026-09-01
- **Предшественник:** [`2026-09-01-tracker-adapters-design.md`](2026-09-01-tracker-adapters-design.md)

## Задача

`/log-day` создаёт карточку сразу в `Done` по факту смерженных pull request'ов.
Отсюда два ограничения, вскрывшиеся на живой работе.

**Планируемая работа на доске не появляется вовсе.** Доска показывает прошлое,
Backlog пуст по построению.

**Работа без pull request'ов невидима.** `collect-window.sh` собирает
исключительно PR через `gh pr list`. Рабочий блок на десять файлов и 1250 строк
не попал на доску, хотя запись создавалась через одиннадцать минут после этих
коммитов.

Нужен обратный поток: план порождает карточку в `Backlog`, карточка проходит
секции по мере работы и закрывается в `Done`.

## Две очереди

Редакция 1 смешивала две разные задачи. Внешнее ревью это вскрыло, и они
разведены.

**Очередь 1 — поток.** План → карточка → секции → закрытие. Идемпотентно, с
предпросмотром и журналом. Карточка находится по gid из плана, поиск не нужен.

**Очередь 2 — обзор.** Локальный индекс, быстрый поиск среди сотен задач,
проактивные подсказки. Ложится на готовый фундамент первой очереди.

Разделение существенно: **для самого потока индекс не нужен**. Карточка
адресуется по gid, записанному в плане, а не разыскивается. Индекс решает
другую задачу — обзор доски целиком, — и её можно решать отдельно.

Ниже описана очередь 1, если не сказано иное. Очередь 2 — в конце, эскизом.

## Решения

### D-01. Карточка проходит весь путь

`Backlog` → `In Progress` → `Done` — одна и та же карточка.

Отвергнуто: заводить отдельную карточку в `Done` по факту работы. Дешевле, но
оставляет два следа одной работы и требует ручной уборки.

### D-02. Двигает человек, не инструмент

Ни одно перемещение не происходит без явного подтверждения.

Причина названа пользователем прямо: инструмент, двигающий карточки сам,
однажды ошибётся, и ошибку потом не найти.

### D-03. Одна карточка на план, шаги — подзадачи

Доска клиентская, карточки на ней крупные. План на двадцать шагов, разложенный
по карточкам, превращает доску из трёх записей в двадцать три.

### D-04. Идентичность: gid плана в заголовке, подзадачи — в карте

`план → карточка` — одна на план, читается глазами при ревью, живёт в заголовке
файла. `шаг → подзадача` — десятки, глазами не читаются, живут в карте рядом.

### D-05. Трекер — истина, локальное — кэш

Истинное состояние всегда в трекере. Файлы и папки отражают его.

Отвергнуто: локальное состояние как истина. Ручная правка в интерфейсе была бы
молча затёрта.

### D-06. Проактивность по проверяемому условию

Инструмент высказывается, когда выполнено проверяемое условие, и молчит
в остальных случаях. Ощущение завершённости у языковой модели порождается
контекстом, а не состоянием мира.

Перенесено в очередь 2.

### D-07. Скрипты владеют локальным, модель — трекером

Новое решение, закрывающее главное замечание ревью.

В worklog детерминированные части реализованы скриптами, а работа с трекером —
документ-рецепт, которому следует модель. Индекс и сверка требуют кода, но
записи в трекер идут через MCP-инструменты, которые вызывает модель, а не шелл.
Значит чистым скриптом эта работа быть не может в принципе.

Разделение труда фиксируется явно:

```text
СКРИПТЫ (детерминированно, без сети, тестируемо)
├── чтение и запись файла плана
├── карта подзадач
├── предпросмотр и его отпечаток
├── журнал операций
├── проверки идемпотентности
└── перенос файла между папками

МОДЕЛЬ (по рецепту адаптера)
└── вызовы трекера и передача ответа обратно скриптам
```

Контракт между ними — файлы, а не память. Скрипт формирует **намерение** в
виде JSON; модель исполняет его вызовами трекера; результат возвращается
скрипту, который записывает исход. Всё, что можно проверить без сети,
проверяется без сети.

### D-08. Идентификатор шага — видимый порядковый, без переиспользования

Шаг помечается коротким маркером в конце строки: `#s3`. Присваивается один раз
при первом прогоне, дальше не меняется. Удалённый шаг забирает свой номер с
собой — переиспользование запрещено, иначе новая подзадача унаследует историю
чужой.

Отвергнуто: хеш текста шага (ломается при правке формулировки) и невидимый
HTML-комментарий (пользователь просил, чтобы связи были видны глазами).

### D-09. Метка происхождения — в описании карточки

Карточка, созданная нами, несёт в описании машиночитаемую строку с путём к
плану. Связь становится двусторонней и проверяемой: план знает gid, карточка
знает план.

Без этого «наша карточка» определялась бы только по наличию `board:` в плане, и
подмена или совпадение gid прошли бы незамеченными.

### D-10. Отменённый план закрывает карточку с явной пометкой

У Asana нет состояния «отменено», есть только `completed`. Карточка отменённого
плана закрывается, а её название получает префикс `Отменено:`. Файл плана
переезжает в `done/`.

Отвергнуто: оставлять карточку в `Backlog` навсегда — она копится и врёт о
намерениях; и закрывать без пометки — доска утверждала бы, что работа сделана.

## Поток

```text
brainstorm → спека → план утверждён
        │
        │  /plan-to-board <план>
        │  сухой прогон: ни одной записи в трекер
        ▼
        <план>.board-preview.md + отпечаток плана
        │
        │  человек читает и подтверждает
        │  отпечаток не совпал → отказ, план изменился после показа
        ▼
        карточка в Backlog + подзадачи по шагам + маркеры #sN в плане
        │
        │  /board-move <план> in-progress
        │  выравнивание → показ намерения → подтверждение
        ▼
        In Progress
        │
        │  /log-day
        │  находит карточку по gid из заголовка плана
        ▼
        Done + story points + результат
```

## Артефакты

| Артефакт | Где | В git |
| --- | --- | --- |
| План | `<plans_dir>/<секция>/<план>.md` | да |
| Связь с карточкой | заголовок плана, поле `board:` | да |
| Маркеры шагов | строки плана, суффикс `#sN` | да |
| Карта подзадач | `<план>.board.json` | да |
| Предпросмотр | `<план>.board-preview.md` | нет |
| Журнал операций | `~/.claude/worklog/journal.ndjson` | нет |

Карта подзадач версионируется намеренно: её `git diff` — доказательство того,
что инструмент сделал.

## Секции и папки

Ревью нашло противоречие в редакции 1: папки объявлялись точным отражением
секций, но `to-do` — это уже перевод из `To Do`.

Исправление: **каноническое имя секции — ключ, а не отображаемое название**.

| Ключ | Папка | Отображаемое имя на доске |
| --- | --- | --- |
| `backlog` | `backlog/` | Backlog |
| `to_do` | `to-do/` | To Do |
| `in_progress` | `in-progress/` | In Progress |
| `review` | `review/` | Ready for Review |
| `done` | `done/` | Done |

Ключи фиксированы, отображаемые имена и идентификаторы секций живут в
конфигурации трекера. Ядро оперирует ключами и никогда — названиями.

### Перемещение по секциям не покрывается возможностью `status`

Ещё одна находка ревью, и существенная. Возможность `status` из предыдущего
дизайна описывает **выражение завершённости** — как трекер показывает, что
работа сделана. Произвольное перемещение между `Backlog`, `To Do` и `Review`
она не покрывает: в адаптере Asana размечены только `done` и `in progress`.

Новой возможности при этом не появляется — секции есть у обоих трекеров, ядро
по ним не ветвится. Появляется требование к конфигурации: полное отображение
пяти ключей на идентификаторы секций, и отказ при неполном отображении.

### Файл едет следом

После успешного перевода карточки файл плана переносится в папку целевой
секции — часть той же операции. Отдельного коммита перенос не требует.

## Идемпотентность и восстановление

Главная дыра редакции 1: карточка создана, подзадача упала, повторный запуск
создаёт дубликаты.

### Правило

Каждая запись идемпотентна по ключу:

- карточка — по полю `board:` в плане. Есть значение → не создавать;
- подзадача — по паре «план, маркер `#sN`» в карте. Есть gid → не создавать.

Повторный запуск `/plan-to-board` на плане с `board:` не создаёт вторую
карточку, а **дозаполняет недостающие подзадачи**.

### Разорванная запись

Состояние «в трекер записано, локально не записано» неизбежно: между двумя
действиями может произойти что угодно.

Журнал пишет **намерение до записи** и **исход после**. Запись без исхода —
признак разрыва. Следующий запуск читает трекер, находит созданное, дописывает
локальные файлы и закрывает запись в журнале. Ничего не пересоздаётся.

Обратный разрыв — «локально записано, в трекере нет» — невозможен по порядку
операций: локальное пишется только после подтверждённого ответа трекера.

### Устаревший предпросмотр

Предпросмотр хранит отпечаток плана. Подтверждение с несовпавшим отпечатком
отклоняется: план изменился после показа, и человек подтверждает не то, что
прочитал.

## Три случая расхождения

Редакция 1 знала два. Ревью нашло третий.

**Кэш устарел.** Карточка в трекере в `Done`, файл лежит в `in-progress/`.
Свершившийся факт: человек подвинул карточку руками. Файл переносится, печатается
строка, пишется журнал. Без остановки — спрашивать про случившееся бессмысленно.

**Намерение конфликтует с реальностью.** Инструмент идёт переводить карточку в
`In Progress`, а она уже в `Done`. Остановка и вопрос.

**Карточка исчезла.** Gid в плане есть, в трекере такой задачи нет: удалена или
перемещена в другой проект. Остановка, сообщение, предложение снять `board:` —
тогда план можно завести заново. Молча пересоздавать нельзя: удаление могло
быть намеренным.

## Судьба плана

**Переименован или перемещён.** Связь не рвётся: gid лежит внутри файла и едет
вместе с ним. Расходится обратная связь — метка происхождения в карточке
указывает на старый путь. Чинится командой перепривязки, которая обновляет
метку. До починки инструмент предупреждает, но не блокирует.

**Удалён.** Карточка остаётся и считается осиротевшей. Ничего не удаляется
автоматически: удаление карточки уничтожает историю, восстановить которую
нельзя.

**Отменён.** См. D-10.

## Шаги: правка, перестановка, удаление

Маркер `#sN` привязан к шагу, а не к его позиции.

- **Текст шага изменён** — связь цела, подзадача переименовывается при следующей
  синхронизации.
- **Шаги переставлены** — ничего не происходит: порядок подзадач в трекере не
  является частью контракта.
- **Шаг удалён** — подзадача не удаляется. Она помечается в карте как
  осиротевшая, и инструмент сообщает об этом. Решение принимает человек.
- **Шаг добавлен** — получает следующий свободный номер, никогда не
  переиспользованный.
- **Шаг без маркера при первом прогоне** — норма: маркеры и присваиваются
  первым прогоном. **Шаг без маркера при последующем** — остановка и вопрос.
  Ревью справедливо указало, что редакция 1 этих двух режимов не различала.

## Отметки шагов и подзадачи

Галочка в плане — источник. Подзадачи в трекере закрываются не непрерывно, а в
момент перевода карточки или её закрытия: одна операция вместо потока мелких
записей.

## Команды

### `/plan-to-board <план>`

Сухой прогон: **ни одной записи в трекер**. Файл предпросмотра при этом
пишется — формулировка редакции 1 «ничего не пишет» была неточной и ревью это
отметило.

После подтверждения: создаёт карточку и подзадачи, записывает `board:` в план,
маркеры в шаги, карту рядом, метку происхождения в описание карточки.

На плане с `board:` — дозаполняет недостающее, не создаёт второй карточки.

### `/board-move <план> <ключ секции>`

Выравнивает локальное представление, показывает намерение вместе с текущим
состоянием карточки, ждёт подтверждения, переводит, переносит файл.

### `/log-day`

Интерфейс не меняется. Если у плана есть `board:`, команда закрывает
существующую карточку вместо создания новой.

## Контракт адаптера

Сверх нынешнего каждый адаптер описывает три операции с явными входами,
выходами и семантикой ошибок:

| Операция | Вход | Выход | Ошибка |
| --- | --- | --- | --- |
| `find` | идентификатор | нормализованная задача | «не найдено» отличается от сетевой ошибки |
| `place` | идентификатор, ключ секции | подтверждение | отказ трекера отличается от неверного ключа |
| `close` | идентификатор, текст, story points | подтверждение | — |

Нормализованная задача одинакова для всех трекеров: идентификатор, название,
ключ секции, признак завершённости, родитель, метка происхождения.

Различие «не найдено» и «сеть недоступна» обязательно: первое означает
исчезнувшую карточку и остановку, второе — повтор позже.

## Границы

- Карточка без метки происхождения и без `board:` в плане — чужая, не трогается.
- Story points ставятся при закрытии, не при планировании.
- Планы, не запущенные командой, на доску не попадают.
- Ни одна запись не идёт без подтверждения человека.
- Карточки никогда не удаляются автоматически.

## Конфигурация

Добавляются:

- `plans_dir` — каталог планов, по умолчанию `docs/superpowers/plans`;
- отображение пяти ключей секций на идентификаторы секций трекера. Неполное
  отображение — ошибка конфигурации, а не повод угадывать.

## Тесты

Список редакции 1 был недостаточен — ревью право.

**Без сети, на подставных ответах:**

- сухой прогон не делает ни одной записи в трекер;
- предпросмотр содержит ровно то, что будет создано;
- подтверждение с несовпавшим отпечатком отклоняется;
- повторный запуск не создаёт дубликатов ни карточки, ни подзадач;
- разорванная запись восстанавливается без пересоздания;
- запись в журнал не появляется при неуспешной операции;
- маркеры присваиваются при первом прогоне и не переиспользуются;
- шаг без маркера при повторном прогоне останавливает работу;
- удалённый шаг оставляет подзадачу осиротевшей, а не удаляет её;
- неполное отображение секций — ошибка конфигурации;
- «кэш устарел» выравнивает папку и не останавливается;
- «намерение против реальности» останавливается и не пишет;
- исчезнувшая карточка останавливает работу;
- карточка без метки происхождения не трогается;
- ошибка переноса файла после успешной записи в трекер оставляет
  восстановимое состояние.

**Контрактные тесты адаптеров** — на подставных ответах трекера: каждая из трёх
операций, оба класса ошибок, нормализованный вид результата.

## Очередь 2, эскизом

Локальный индекс задач проекта для быстрого обзора: gid, название, ключ секции,
признак завершённости, родитель, план. Операции `refresh` и `find`. Открытым
остаётся то, что ревью справедливо назвало: пагинация, частичный ответ,
недоступность трекера, защита прежнего индекса от повреждения.

Проактивные подсказки по проверяемым условиям: что в работе на старте сессии,
все ли шаги закрыты, не висит ли план без коммитов дольше порога.

Запасной источник доказательства при закрытии, когда pull request'ов нет:
коммиты ветки плана с момента расхождения с `main`. Определить окно и команду
сбора. В очереди 1 не нужен: правило «прямой коммит в `main` запрещён» делает
pull request'ы существующими по построению.

## Открытые вопросы

1. **Границы `refresh`** — весь проект или только незакрытые задачи. Очередь 2.
2. **Предпросмотр файлом или страницей.** Принят файл как тестируемый; к
   вопросу можно вернуться.
