# Plan → Board: планируемая работа на доске трекера

- **Статус:** дизайн утверждён, реализация не начата
- **Дата:** 2026-09-01
- **Предшественник:** [`2026-09-01-tracker-adapters-design.md`](2026-09-01-tracker-adapters-design.md)

## Задача

`/log-day` создаёт карточку сразу в `Done` по факту смерженных pull request'ов.
Из этого следуют два ограничения, которые вскрылись на живой работе.

**Планируемая работа на доске не появляется вовсе.** Доска показывает прошлое,
а не то, чем занят человек сейчас. Backlog пуст по построению.

**Работа без pull request'ов невидима.** `collect-window.sh` собирает
исключительно PR через `gh pr list`; коммитов он не видит. В проекте, где
коммиты уходили прямо в `main`, целый рабочий блок — сверка ТЗ с архитектурным
базисом, десять файлов, 1250 строк — не попал на доску вообще, хотя запись
создавалась через одиннадцать минут после этих коммитов.

Нужен обратный поток: план порождает карточку в `Backlog`, карточка проходит
секции по мере работы и закрывается в `Done`.

## Решения

Шесть решений, принятых в брейншторме 2026-09-01. Каждое приведено с
обоснованием, потому что альтернативы были живыми.

### D-01. Карточка проходит весь путь

`Backlog` → `In Progress` → `Done` — одна и та же карточка, а не отдельная
запись на каждом этапе.

Отвергнуто: создавать намерение в `Backlog`, а по факту работы заводить новую
карточку в `Done`. Это дешевле — не нужна идентичность, — но оставляет на доске
два следа одной работы и требует ручной уборки.

### D-02. Двигает пользователь, не инструмент

Ни одно перемещение не происходит без явного подтверждения человека.

Причина сформулирована пользователем прямо: инструмент, бесконечно двигающий
карточки сам, однажды ошибётся, и ошибку потом не найти. Автономность здесь
дешевле в моменте и дороже в сумме.

### D-03. Одна карточка на план, шаги — подзадачи

Не карточка на фазу и не карточка на шаг.

Причина в масштабе доски: она клиентская, карточки на ней крупные и написаны
для менеджера. План на двадцать шагов, разложенный по карточкам, превращает
доску из трёх записей в доску из двадцати трёх — и именно этого пользователь
избегал, отказавшись от GitHub Issues.

Возражение, принятое сознательно: крупная карточка висит в `In Progress`
долго, и по секциям движения не видно. Лечится тем, что прогресс читается
внутри карточки по закрытым подзадачам.

### D-04. Идентичность: gid плана в заголовке, подзадачи — в карте

Связей две, и природа у них разная.

`план → карточка` — одна на план, человек читает её глазами при ревью. Живёт
в заголовке файла плана: видна в `git diff`, ошибка в ней замечается.

`шаг → подзадача` — десятки на план, глазами всё равно не читаются. Живут в
отдельном файле-карте рядом с планом.

Отвергнуто: всё в файле плана — тело обрастает служебными числами; всё в
карте — главная связь перестаёт быть видна при ревью.

### D-05. Трекер — истина, индекс и папки — кэш

Локальный индекс существует ради скорости чтения на сотнях задач. Истинное
состояние всегда в трекере.

Отвергнуто: индекс как истина с синхронизацией по команде. Быстрее всего, но
ручная правка в интерфейсе может быть молча затёрта — ровно тот класс
невидимой ошибки, которого требовалось избежать.

### D-06. Проактивность по проверяемому условию, не по ощущению

Инструмент предлагает следующее действие, когда выполнено **проверяемое**
условие, и молчит в остальных случаях.

Исходная формулировка задачи звучала как «предлагай, когда есть ощущение, что
завершено». Ощущение у языковой модели порождается контекстом, а не состоянием
мира, — это механизм галлюцинации, а не наблюдения.

## Поток

```text
brainstorm → спека → план утверждён
        │
        │  /plan-to-board <план>        сухой прогон, ничего не пишет
        ▼
        <план>.board-preview.md
        │
        │  человек читает и подтверждает
        ▼
        карточка в Backlog + подзадачи по шагам
        │
        │  /board-move <план> in-progress
        │  выравнивание → показ намерения → подтверждение
        ▼
        In Progress
        │
        │  /log-day
        │  находит карточку по gid из заголовка плана
        ▼
        Done + story points + результат
```

Каждая стрелка, за которой стоит запись в трекер, проходит через подтверждение.

## Артефакты

| Артефакт | Где | В git |
| --- | --- | --- |
| План | `<plans_dir>/<секция>/<план>.md` | да |
| Связь с карточкой | заголовок плана, поле `board:` | да |
| Карта подзадач | `<план>.board.json` | да |
| Предпросмотр | `<план>.board-preview.md` | **нет** |
| Индекс | `~/.claude/worklog/index/<tracker>-<project>.json` | нет |
| Журнал | `~/.claude/worklog/journal.ndjson` | нет |

Предпросмотр не версионируется: это артефакт момента, перезаписываемый при
каждом сухом прогоне. Карта подзадач версионируется намеренно — её `git diff`
служит доказательством того, что инструмент сделал.

Индекс и журнал живут вне репозитория: это кэш и операционный лог, а не данные
проекта.

## Папки как отражение секций

```text
<plans_dir>/
├── backlog/
├── to-do/
├── in-progress/
├── review/
└── done/
```

Имена повторяют секции доски один в один, без перевода: любой перевод создаёт
вопрос «а это какая колонка».

Папка — **не состояние, а отражение**, того же статуса, что индекс. Перед любой
операцией по gid инструмент выравнивает локальное представление по трекеру.

### Два разных случая расхождения

Их нельзя путать, и ранняя версия дизайна их путала — предлагала останавливаться
в обоих, из-за чего человек утыкался бы в вопросы на ровном месте.

**Кэш устарел.** Карточка в трекере в `Done`, а файл плана лежит в
`in-progress/`. Это свершившийся факт: человек подвинул карточку руками.
Инструмент переносит файл, печатает одну строку и пишет в журнал. Не
останавливается — спрашивать про уже случившееся бессмысленно.

**Намерение конфликтует с реальностью.** Инструмент идёт переводить карточку в
`In Progress`, а она уже в `Done`. Это не устаревший кэш, а противоречие:
запрошенное действие не имеет смысла в текущем состоянии. Остановка и вопрос.

### Файл едет следом

После успешного перевода карточки файл плана переносится в папку целевой
секции — это часть той же операции, а не отдельный шаг. Отдельного коммита
перенос не требует: он едет вместе с той работой, которая и так шла.

## Индекс

### Что хранит

На задачу: `gid`, `name`, `section`, `completed`, `parent`, и `plan` — путь к
плану, если карточка создана нами. Ничего больше: описания, комментарии и
история в индекс не попадают.

Триста задач — порядка шестидесяти килобайт. `grep` по такому файлу
мгновенен.

### Операции

- `refresh` — один запрос списка задач проекта, полная перезапись индекса.
- `find <текст>` — поиск по локальному файлу, без сети.
- `verify <gid>` — один точечный запрос, сравнение с индексом. Вызывается
  перед каждой записью.

### Почему индекс, а не контекст

Держать сотни задач в контексте модели — это одновременно источник тормозов и
галлюцинаций: ответ начинает браться из того, что читалось раньше, а не из
состояния мира. Индекс существует затем, чтобы ответ приходил из вывода
скрипта.

## Команды

### `/plan-to-board <план>`

Сухой прогон: читает план, определяет шаги, формирует предпросмотр и
**ничего не пишет**. Человек читает файл предпросмотра и подтверждает. Только
после подтверждения создаётся карточка и подзадачи, gid записывается в
заголовок плана, карта подзадач — рядом.

### `/board-move <план> <секция>`

Выравнивает локальное представление, показывает намерение вместе с текущим
состоянием карточки, ждёт подтверждения, переводит.

### `/log-day`

Интерфейс не меняется. Меняется поведение: если у плана есть `board:`, команда
находит существующую карточку и закрывает её, а не создаёт новую.

## Чем закрывается карточка, если pull request'ов нет

Исходная жалоба была именно об этом: работа без pull request'ов не попадает на
доску. Карточку из плана этот дизайн создаёт, но закрытие по-прежнему опирается
на `collect-window.sh`, который видит только PR.

**Основной источник доказательства остаётся прежним** — смерженные pull
request'ы. Он не заменяется: ссылка на PR в карточке это то, что делает запись
проверяемой для заказчика.

**Запасной источник — сам план.** Если у карточки есть `board:`, а в окне не
нашлось ни одного PR, текст закрытия строится из закрытых шагов плана и
коммитов ветки, а поле ссылок остаётся пустым и помечается как таковое. Молча
подставлять коммиты вместо PR нельзя: это разные по надёжности свидетельства.

Оговорка о причине: в породившем задачу проекте PR'ов не было потому, что
коммиты уходили прямо в `main` вопреки собственной конвенции репозитория. Это
чинится дисциплиной, а не инструментом, и запасной источник нужен не как
замена, а на случай работы, у которой pull request'а быть не может, — правки
документов, разовые операции.

## Что требуется от адаптеров

Сверх нынешнего контракта каждый адаптер должен уметь три операции:

1. **найти задачу по идентификатору** — для `verify`;
2. **перечислить задачи проекта** — для `refresh`;
3. **перевести задачу между секциями** — уже покрыто возможностью `status`.

Новых ключей возможностей не появляется: перечисленное умеет любой трекер, и
ядро по этому не ветвится. Это разделы внутри файла адаптера, а не флаги.

## Стабильный идентификатор шага

Связь `шаг → подзадача` не может опираться на текст шага: текст правится, и
связь молча указала бы не туда.

**Решение:** при создании карточки каждому шагу присваивается короткий
неизменяемый идентификатор, который записывается в план рядом с шагом.
Идентификаторы не переиспользуются: удалённый шаг забирает свой номер с собой.

Расхождение падает громко: шаг в плане есть, идентификатора нет — остановка и
вопрос, а не тихое досоздание подзадачи.

## Проактивность: условия

Инструмент высказывается ровно в трёх случаях, и каждый проверяем без обращения
к памяти модели.

1. **В начале сессии** — читает `in-progress/` и одной строкой сообщает, какой
   план в работе и сколько шагов закрыто.
2. **Все шаги плана отмечены** — предлагает перевести карточку дальше. Именно
   предлагает.
3. **План висит в `in-progress` без коммитов дольше порога** — сообщает.
   Порог задаётся в конфигурации, по умолчанию трое суток. Проверяется через
   `git log` по файлу. Условие в списке проверяемых обязано быть измеримым:
   «несколько дней» им не является.

Известное ограничение: галочки в плане ставит та же модель, что и проверяет
условие. Условие проверяемое, но не независимое. Полностью лечится только
закрытием шага по зелёным гейтам, а не по отметке; принято как есть с
возвратом к вопросу, если начнёт врать.

## Границы

- Карточка без `board:` в плане считается чужой — не трогается вообще.
- Story points ставятся при закрытии, не при планировании: так устроена доска
  сегодня, и оценка до работы всё равно врёт.
- Планы, которые не запущены командой, на доску не попадают. Backlog отражает
  то, за что взялись, а не все накопленные намерения.
- Ни одна запись не идёт без подтверждения человека.

## Конфигурация

Добавляется `plans_dir` — путь к каталогу планов относительно корня проекта.
Значение по умолчанию `docs/superpowers/plans`. Имена подпапок выводятся из
секций доски, а не задаются отдельно.

## Тесты

- `plan-to-board` в сухом режиме не делает ни одного запроса на запись.
- Предпросмотр содержит ровно то, что будет создано: название, описание,
  список подзадач, целевую секцию.
- Расхождение «кэш устарел» выравнивает папку и не останавливается.
- Расхождение «намерение против реальности» останавливается и не пишет.
- Шаг без идентификатора приводит к остановке, а не к досозданию.
- Карточка без `board:` в плане не трогается.
- Индекс на трёхстах задачах ищется без обращения к сети.
- Каждая запись оставляет строку в журнале.

## Открытые вопросы

1. **Формат идентификатора шага** — короткое число, хеш или порядковый номер с
   защитой от переиспользования. Влияет на читаемость плана.
2. **Что делать с планом, который отменили.** Карточка остаётся в `Backlog`
   навсегда или закрывается как отменённая — у Asana для этого нет отдельного
   состояния, только `completed`.
3. **Границы `refresh`.** Тянуть весь проект или только незакрытые задачи.
   На трёхстах задачах разница невелика, на трёх тысячах — существенна.
4. **Предпросмотр файлом или страницей.** Принят файл как тестируемый вариант;
   страница нагляднее и к вопросу можно вернуться.
